来源输入持久化事实派生结果控制/任务产品输出

当前最重要的实体

sources → photos一对多。photos 保存 source_id + relative_path，是物理文件索引的事实主线。
photos → logical_id当前用同一个 logical_id 表达 RAW/JPEG/HEIF 等物理 variant 属于同一逻辑照片。
photos → photo_assets缩略图和预览是可重建缓存，不应成为照片事实的唯一来源。
analysis_jobs → results/events分析运行和分析结果分开保存，结果再被 materializer 投影成标签/人物等产品数据。
Views ≠ source of truthTimelinePhoto 是查询 DTO；Library、Sources、Similar、People 是消费方。

当前真实数据流

01 来源用户选择一个或多个 Source 根目录；扫描递归发现文件。
02 索引写入 sources / photos，并解析 EXIF、尺寸、mtime、extension。
03 归组按同拍逻辑生成 logical_id，查询时合并或展开 variants。
04 分析analysis_jobs 驱动质量、标签、人脸、embedding 等结果。
05 输出TimelinePhoto DTO 驱动浏览；Reorganize 生成计划后再 copy/move。

对本次照片组织功能的启发

事实层和计划层要分开ReorganizePlanEntry 是一次操作的候选结果，不应直接覆盖 photos 的事实记录；执行成功后再刷新/重扫索引。
规则应该产出可解释路径日期、格式、相机、镜头都来自 photos/EXIF；缺失值要有明确 Unknown/Unsorted 策略。
logical_id 是当前最自然的归组边界RAW+JPEG+HEIF 先作为同一逻辑照片的 variants；显示合并/分开属于查询策略。
移动不是分析结果物理 copy/move 属于控制层操作，需要确认、冲突策略、失败记录和重扫验证。

脑暴需要先决定

Q1 · 组织对象规则是作用于每个物理 variant，还是先按 logical photo 分组再决定整组目标路径？
Q2 · 移动后的 Source目标目录是新建一个 source，还是更新原 source 的 root/path 并继续作为同一个来源？
Q3 · 关联置信度RAW/JPEG 只按文件名+时间自动关联，还是低置信度必须进入人工确认队列？

建议的下一步拓扑

建议新增“组织计划”作为独立控制事实：organization_plans → organization_entries → execution_runs。photos 仍是文件事实；logical_id 仍是照片关系；执行完成后通过 source/path reconciliation 更新 photos。这样 dry run 可以反复修改和预览，execute 只是消费已确认的 plan，不把 UI 当前状态直接当成移动指令。
