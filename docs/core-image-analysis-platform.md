# Core Image Analysis Platform

> 算法层与能力层的定位与边界。回答 Gala 的长期核心：建设可复用、可扩展、可对外调用的图像分析与处理能力层。
> 上层架构见 [technical-architecture.md](technical-architecture.md)；能力结果如何接入数据与任务系统见 [data-and-control-design.md](data-and-control-design.md)。

在这个定位之上，`People` 和 `Similar` 被定义为建立在能力层之上的功能模块，而不是能力层本身。

---

## 一句话结论

Gala 的长期核心，不是零散地叠加若干 AI feature，而是建设一套可复用、可扩展、可对外调用的图像分析与处理能力层。

这套能力层为上层模块提供统一的图像理解、图像检索、图像处理建议与任务执行基础。`People`、`Similar`、未来的整理建议、智能筛选、自动生成合集与外部 agent 工作流，都应建立在这同一层能力之上。

---

## 核心结论

### 1. Gala 需要的是能力层，而不是单点功能实现

项目的核心方向已经明确：优先建设图像分析与处理能力层，而不是分别为 `People`、`Similar` 或其他单个页面各自实现一套底层逻辑。

能力层应沉淀通用能力，供多个产品模块共享。

### 2. People 和 Similar 是上层功能模块

`People` 和 `Similar` 都是产品层模块。它们依赖能力层提供稳定的分析结果、检索能力和解释信息，但它们本身不定义底层分析抽象。

这意味着：

- `People` 是能力层在“人物组织与浏览”方向上的一个功能模块。
- `Similar` 是能力层在“视觉关系发现与筛选”方向上的一个功能模块。
- 后续新增的能力消费方，也应采用同样的结构组织。

### 3. 能力层是产品内外共享的基础设施

能力层不仅服务于 Gala 自己的桌面产品界面，也应服务于自动化流程和外部调用方。

因此它的定位不是“应用内部工具模块”，而是产品核心基础设施。

### 4. Provider 是实现手段，不是顶层架构中心

macOS Vision、跨平台本地模型、远程推理服务都只是能力来源。顶层设计不应围绕某一个 provider 展开，而应围绕能力边界、任务模型和结果复用来组织。

---

## 为什么需要这层能力

Gala 未来需要持续支撑以下四类需求：

- 图像理解：识别人、场景、物体、文本、构图和风格线索。
- 图像检索：支持相似图发现、近重复检测、连拍分组和跨时间跨度的视觉召回。
- 图像处理：为裁切、增强、去重、整理和批量决策提供分析依据。
- 外部智能调用：允许 Hermes、OpenClaw 或其他 agent 把 Gala 当成图像分析引擎来调用。

如果这些能力分别附着在单个产品 feature 上，能力无法复用，结果无法沉淀，外部系统也无法稳定接入。独立能力层正是为了解决这个问题。

---

## 平台定位

### 面向产品

从产品视角看，这套能力层负责提供可消费的分析结果，而不是直接决定页面长什么样。

产品模块可以基于它构建：

- 人物浏览与管理
- 相似图发现与筛选
- 智能整理建议
- 搜索与推荐
- 自动生成主题、合集和回忆

### 面向工程

从工程视角看，这套能力层是一个独立边界明确的核心子系统。它负责接收分析请求、编排底层能力、复用已有结果，并向上层输出稳定语义，而不是把分析逻辑分散塞进 UI、扫描流程或单个命令入口。

### 面向外部系统

从生态视角看，这套能力层还应具备被外部程序调用的能力。外部 agent 不应该绕过 Gala 自己重建一套图像理解逻辑，而应该直接消费 Gala 已经沉淀出的能力与结果。

---

## 分层结构

### 1. 产品模块层

这一层定义用户最终看见的功能与交互。

典型模块包括：

- `People`
- `Similar`
- 搜索与筛选
- 推荐与整理建议

这一层关注的是体验、解释和操作入口，不直接关心底层究竟由哪个 provider 完成分析。

### 2. 能力编排层

这是能力层的核心调度部分。

它负责：

- 接收来自产品模块或外部调用方的请求。
- 将上层需求翻译成分析任务或查询任务。
- 选择合适的执行路径。
- 决定结果是实时返回、后台执行还是复用已有结果。

这层的职责是把“业务诉求”转化为“可执行的能力请求”。

### 3. Provider 层

Provider 层负责实际执行图像分析。

这里允许存在多种实现：

- 系统原生能力，例如 macOS Vision。
- 跨平台本地模型能力。
- 远程推理能力。

Provider 的存在是为了实现能力，而不是主导能力边界。

### 4. 结果沉淀层

能力层必须能够沉淀和复用已经产生的分析结果。

这层的价值在于：

- 避免重复计算。
- 让人物归并、相似关系和推荐结果持续收敛。
- 让产品层与外部调用方共享同一套分析事实。
- 支撑长期的自动化与知识积累。

### 5. 外部调用层

能力层应允许进程外调用，而不只局限于 Gala 前端的进程内使用。

这层需要提供的是稳定的能力入口和结果语义，而不是暴露底层 provider 细节。

---

## 能力层应该提供什么

在当前设计共识下，能力层至少应覆盖以下能力域：

### 图像理解能力

- 人脸和人物相关理解。
- 场景、物体、文本与风格线索提取。
- 质量、构图或审美相关分析。

### 图像关系能力

- 相似图检索。
- 近重复检测。
- 连拍关系发现。
- 长跨度语义相似召回。

### 图像处理辅助能力

- 整理建议。
- 去重建议。
- 批量处理决策依据。
- 后续编辑或增强建议。

### 任务与解释能力

- 接收分析任务并反馈状态。
- 输出可复用的分析结果。
- 提供结果解释、置信度和可追踪语义。

这里的重点不是某一个具体模型，而是能力层对外提供稳定的能力边界。

---

## 建立在能力层之上的功能模块

## People

`People` 是建立在能力层之上的人物组织模块。

它的职责不是重新定义人脸识别或人物归并逻辑，而是把能力层已经提供的人物相关结果组织成用户可理解、可浏览、可操作的产品体验。

对于 `People` 模块来说，能力层至少需要向上提供：

- 人脸发现能力。
- 人物特征归并能力。
- 跨照片的人物身份聚合能力。
- 结果解释与后续修正的基础。

`People` 模块本身更关注：

- 如何展示人物集合。
- 如何让用户确认、修正或使用人物结果。
- 如何把人物结果接入搜索、筛选、推荐和整理流程。

### People 与 tag 的关系

tag 可以作为 `People` 结果的一种展示、筛选或交互入口，但 tag 不是人物能力本身。

原因在于，人物是一类长期实体，而 tag 是自由文本标签。二者的生命周期、稳定性、解释语义和后续演进方式不同。

因此在设计上应坚持：

- 人物识别与人物归并属于能力层结果。
- tag 只是一种消费这些结果的产品投影方式。

---

## Similar

`Similar` 是建立在能力层之上的视觉关系发现模块。

它负责把能力层产出的图像关系结果组织成用户可消费的浏览、筛选和决策体验，而不是自行维护一套相似度计算体系。

对于 `Similar` 模块来说，能力层至少需要向上提供：

- 图像之间的视觉关系基础。
- 近重复与连拍关系。
- 长跨度语义相似召回。
- 相似原因的解释信息。

`Similar` 模块本身更关注：

- 如何帮助用户完成连拍筛选。
- 如何帮助用户发现跨时间的视觉关联。
- 如何把相似关系用于整理、推荐和回忆生成。

### Similar 包含两类价值

`Similar` 不应被理解成单一功能点，而应被理解成建立在统一能力层上的一个功能族。

它至少包含两类产品价值：

- 工作流导向的相似，例如连拍筛选、近重复清理。
- 发现导向的相似，例如跨时间的风格、构图、人物或场景相似。

这两类价值依赖同一套底层能力，但在产品体验上会被组织成不同的使用方式。

---

## Provider 战略

### macOS Vision 的位置

macOS Vision 是高价值 provider，但它的角色是本地桌面环境下的优先实现之一，而不是顶层架构中心。

它适合在 macOS 环境中承担高性能、低延迟的本地能力实现，但顶层设计不能被它的 API 边界反向塑形。

### 跨平台本地 provider 的位置

如果 Gala 未来要支持跨平台桌面和服务化部署，就必须保留一条不依赖系统原生框架的主干路径。

这类 provider 的价值在于提供统一、可迁移、可扩展的长期底座。

### 远程 provider 的位置

远程 provider 不只是为了未来云端化，也用于支撑低性能设备、后台重任务和外部自动化调用。

因此远程能力应从设计上预留，而不是在后续扩展时临时补上。

---

## 外部调用原则

能力层需要支持两种调用方式：

- 进程内调用：供 Gala 自身界面和本地工作流使用。
- 进程外调用：供 agent、脚本、守护进程和后台服务使用。

对外暴露的应是：

- 稳定的能力描述。
- 稳定的任务入口。
- 稳定的结果查询语义。
- 稳定的解释与状态信息。

不应暴露成对外契约的内容包括：

- 当前具体使用哪个 provider。
- 当前模型文件的组织方式。
- 当前索引是本地还是远程实现。

这样可以保证外部系统依赖的是能力语义，而不是底层实现偶然细节。

---

## 任务与结果原则

能力层不应被建模为一组只有同步调用的函数集合，而应被理解为一个任务驱动、结果可复用的系统。

这意味着：

- 轻量请求可以实时完成。
- 重分析任务可以异步执行。
- 已有结果应优先被复用，而不是重复全量计算。

对于上层模块和外部调用方来说，能力层输出的不只是某次调用的即时返回值，还包括长期可沉淀、可复用、可解释的分析资产。

---

## 对当前代码结构的约束

现有后端以扫描、存储和命令为主，引入独立能力层时应坚持：

- 不把核心分析逻辑直接塞进现有 `commands`。
- 不把扫描流程和高级分析流程绑死在一起。
- 不让单个功能模块反向定义底层能力抽象。

更合理的结构：扫描负责发现文件和建立基础索引；能力层负责理解、关联、解释与分析任务；产品模块负责组织体验和消费结果。
